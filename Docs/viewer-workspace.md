# Viewer workspace

The desktop shell uses React with shadcn-style components built on Base UI. The Three.js renderer and replay engine remain independent. Profile settings and detailed statistics retain their existing data owners; their controls mount the same React Select and Switch components as the shell. The replaced RHU dropdown, toggle and navigation implementations are removed.

The top bar contains recordings, replay profile, live connection and window controls. One left navigation opens events, bookmarks, whole-run summary, detailed player statistics, item finder, capture, chat, diagnostics and settings. Only one side panel is open at a time. Language lives in settings, including settings opened from the recording library.

Run summary uses player columns and metric rows, including names of departed players from the retained Steam-ID roster. Detailed player statistics show their current replay timestamp. Both surfaces read the same tracker; opening the detailed panel does not add empty players to snapshots. Missing host-dependent damage/kills/packs and missing teammate accuracy are shown as unavailable rather than zero; observed nonzero totals remain visible. The source explanation describes the current recorder's host/owner capture limits, not a fundamental inability of clients to observe game events.

Client observations: new recordings contain an empty `Vanilla.StatTracker.Client` capability header, `EnemyDeath` events (32-bit enemy ID), and `PackConsumed` events (32-bit player ID, one-byte pack type matching the Pack type table). Confirmed deaths require a completed transition into Dead and are deduplicated per tracked spawn, including native despawn during the transition. Ordinary removals do not count. Pack consumption requires the locally owned player's supported pack contents to decrease during ApplyPack; cancelled interactions and remote owners do not count. These events are local only, with no RNet broadcast or merging into host totals. The viewer shows confirmed deaths separately from attributed kills, and local pack consumption separately from packs received. Missing capability in existing recordings means unavailable, not zero. Other players' consumption remains unavailable.

Current recording limits: damage and resource-effect hooks still require the master and broadcast through RNet; precise shot information is produced by each weapon owner. Revives and some other events can exist in client-only recordings. Existing recordings merge deaths and ordinary despawns and cannot recover the new counts. Confirmed deaths are observations during capture, not a guaranteed level total. Local pack counts describe consumed uses, not confirmed remote receipt, healing amounts or transfer attribution. Those uncertain measurements are not inferred. Native game integration still requires the client-only checks in `session-validation.md`.

The bottom transport contains start/end, five-second back/forward, previous/next tick, play/pause, whole-second timestamps, speed and an explicitly labeled player-follow selector with free camera. It has no time-jump form or A–B selection. Keyboard shortcuts are Space, Left/Right, Shift+Left/Right and Home/End; input fields, buttons, selects and dialogs keep their own keyboard behavior. Internal timestamps retain original precision.

Disk recordings expose their full duration before the playback view opens: container metadata supplies it, while raw and ZIP imports scan frame headers without parsing payloads. The timeline stays fixed and distinguishes the loaded prefix from pending data, with a percentage and loaded timestamp. Playback and seeking stop at the loaded boundary until parsing advances. Opening shows extraction/header-scan progress and the scene-loading stage; live streams retain a growing duration. Failed parsing never labels unread data as loaded.

Event filtering is presentation-only. Shots never appear in event lists, event counts, filters or the timeline. Heartbeats, damage and technical traffic are opt-in; downed players and Scout screams remain visible. The event list and timeline use the same filter. Timeline marks within three CSS pixels share a column; markers take precedence. No events are dropped from the replay engine.

The vanilla profile annotates the event index with participant identities while the parser has the event-time snapshot. Player IDs, alert slots and marker Steam IDs resolve through their own namespaces; mine damage resolves through its recorded owner. This avoids assigning a later occupant of a slot to an earlier event. The UI searches and displays these captured names; missing identities remain explicitly labeled by type and ID, not guessed. This adds no recorder fields or model resources.

Alert and wakeup events within two seconds of the group's first event share an expandable row. Alert targets stay separate, important intervening events end the group, and each child retains its original timestamp and locate action. Filtering precedes grouping. The counter reports both matching event count and displayed group rows; the timeline uses each group's first event. Raw events remain unchanged for playback and statistics.

Clicking an event row or Locate pauses three seconds before the event, clamped to the recording or clip start, and follows its historical subject. Player IDs stay pinned across slot reuse; revives, resource transfers and damage focus the recipient. Enemy subjects are tracked by ID, and event labels include their catalog type and instance ID. Teammate revive actions and player-revived state events have distinct labels. Missing location data is reported without guessing an ID namespace. A late snapshot read cannot override a newer event click, seek, recording switch or manual camera input.

The camera selector starts in Auto events mode. During forward playback it selects downed players, Snatcher grabs, Scout screams, revives, markers and enemy alerts. It normally holds a subject for at least six real viewing seconds; a more urgent event can interrupt after three seconds. Repeated events about the same subject do not restart the camera move. Noise, paused playback, reverse playback and seeking do not trigger a backlog of camera cuts. Nearby target changes ease over 650 ms; long map jumps, dimension changes and reduced-motion mode use a direct cut. Manual selection, event clicks, movement, orbiting or zooming takes control until Auto events is selected again. Free camera preserves the current world position and rotation.

All app file selection, directory selection, saving, overwrite confirmation and recycling confirmation use in-app dialogs. Electron owns directory enumeration and path validation. Each pending dialog belongs to its requesting WebContents, settles on cancellation/navigation/destruction and validates the result before returning it to the file operation. No native dialog fallback is used. Toasts announce transient results; persistent diagnostic and folder health information remains in its relevant panel. Tooltips work on pointer hover and keyboard focus and show shortcuts.

Audio is not currently recorded or played. Audio controls and volume shortcuts are omitted by request.

Select a player, then enable First person beside the camera selector to follow their recorded look direction. The camera uses estimated standing/crouching/downed eye heights. The followed original player model is hidden to prevent camera obstruction. This does not reproduce the game camera, ADS, shake or first-person weapon animation. Turning off First person restores the original third-person model; free camera and Auto events release player follow.

With the replay canvas focused, Shift raises the free camera and Ctrl lowers it; F also toggles playback. WASD moves only along the horizontal plane, using camera yaw regardless of pitch. Holding movement ramps from 1x to 4x base speed over three seconds; releasing movement or losing focus resets the ramp. Diagonal movement has the same speed as straight movement. The mouse wheel still adjusts base speed. Space retains its playback shortcut inside and outside the canvas.

Windows portable releases use `Tools/Release/publish-viewer.ps1` after Forge packaging and desktop acceptance. The release root contains `Open Viewer.lnk`, `README.txt` and `app/`. The script verifies every runtime file with SHA-256 and leaves any existing or running release untouched.

Validation: `node --test --test-isolation=none Tests/Viewer/*.test.cjs`; `Tests/Viewer/electron-smoke.cjs` under Electron uses offscreen rendering and the actual preload/IPC/profile. It exercises custom dialogs, localization, navigation, event filtering, notifications, rendering, seeking and rapid replay switching. An optional third CLI argument supplies a real recording for player-follow and keyboard checks. Test exports stay under `artifacts/tests/electron`.

`Tests/Viewer/statistics-smoke.cjs` under Electron checks the built summary at desktop and narrow window sizes in English and Chinese. Statistics unit tests cover missing capture, historical names, read-only snapshot access and damage-to-kill/assist aggregation. Its layout fixtures are illustrative test data.

`dotnet run --project Tests/ClientStats/ClientStats.Tests.csproj` runs the production Harmony callbacks against game boundary stubs, covering ownership, cancellation, final resource charge, wire payloads, rejected death transitions, duplicate callbacks, native despawn and reused IDs. It does not simulate native ApplyPack internals. Viewer statistics tests cover the new header, parser, separate counters and unavailable teammate data.

Source ownership: `interface/src/features/` contains playback, library, bookmarks and statistics. `components/layout/` owns workspace navigation; `components/dialogs/` file dialogs; `components/feedback/` notifications and tooltips; `components/ui/` shared Base UI primitives. The bundle entry only mounts features and exposes the profile bridge. Electron dialog requests and validation live in `electron/src/replay/dialogs.cts`.
